# Функциональное техническое задание (BRD / FRD)

**Документ:** `docs/requirements/edi-carrier-integration-service-functional-spec.md`
**Статус:** Approved for Development
**Сервис:** edi-carrier-integration-service (Поддомен: Warehouse Cross-Docking & B2B EDI)

## 1. Введение и Назначение Сервиса

### 1.1 Бизнес-контекст
Крупные морские линии (Maersk, MSC), национальные Ж/Д перевозчики и государственные таможенные органы не интегрируются по современным REST/JSON API. Они обмениваются закрытыми промышленными форматами текстовых сообщений (EDIFACT, ANSI X12) через защищенные протоколы связи (AS2, SFTP). `edi-carrier-integration-service` изолирует внутреннюю микросервисную архитектуру от устаревших внешних стандартов, работая как двусторонний двунаправленный «переводчик».

### 1.2 Проблемы, которые решает сервис
*   **Совместимость с Legacy-системами:** Возможность автоматического обмена документами и статусами с партнерами без требования к ним обновлять их IT-инфраструктуру.
*   **Гарантированная юридическая доставка:** Поддержка квитирования и подтверждений получения сообщений (MDN — Message Disposition Notification в протоколе AS2).
*   **Нормализация формата:** Преобразование разрозненных EDI-сообщений внешнего мира в единый канонический формат внутренних Kafka-событий платформы.

## 2. Доменная модель и Сущности (Domain Entities)

Сервис оперирует сущностями B2B-обмена и трансляции:

```text
 ┌──────────────────────┐       1..N      ┌──────────────────────┐
 │    EDIPartnerProfile ├────────────────►│      EDIMessage      │
 └──────────────────────┘                 └──────────┬───────────┘
                                                     │ 1
                                                     │ 1..N
                                                     ▼
                                          ┌──────────────────────┐
                                          │  MappingSpecification│
                                          └──────────────────────┘
```

*   **EDIPartnerProfile (Профиль B2B-партнера):** Настройки взаимодействия с контрагентом (портовый терминал, морская линия, таможня). Содержит сертификаты шифрования, AS2-идентификаторы (AS2 ID), URL-адреса endpoints и используемый стандарт (EDIFACT / ANSI X12).
*   **EDIMessage (EDI-сообщение):** Входящий или исходящий пакет обмена. Хранит сырой текстовый файл (например, EDIFACT IFTMIN или DESADV), его уникальный контрольный номер (Control Number), текущий статус обработки и признак квитирования (MDN).
*   **MappingSpecification (Спецификация маппинга):** Правило трансформирования полей из формата EDI (например, элемент NAD+CZ) во внутреннее DTO/Kafka-сообщение и наоборот.

## 3. Бизнес-логика и Жизненный Цикл

### 3.1 Жизненный цикл исходящего EDI-сообщения (EDIMessage)

```text
 [CREATED] ──(Маппинг в EDIFACT)──► [PARSED] ──(Шифрование S/MIME)──► [SENT_VIA_AS2] ──(Получен MDN-чек)──► [ACKNOWLEDGED]
                                                                          │
                                                                          │ (Таймаут / Ошибка AS2)
                                                                          ▼
                                                                  [DELIVERY_FAILED]
```

### 3.2 Основные бизнес-сценарии (Use Cases)

**UC-1: Отправка инструкции на погрузку контрагенту (Outbound Shipping Instruction)**
1.  Внутренний сервис `warehouse-crossdock-service` генерирует событие `ShipmentReadyForDepartureEvent`.
2.  `edi-carrier-integration-service` подхватывает событие, находит профиль партнера-перевозчика и трансформирует JSON-сообщение в стандарт EDIFACT IFTMIN (Instruction message).
3.  Сообщение подписывается цифровой подписью, шифруется S/MIME и отправляется партнеру по протоколу AS2.
4.  Сервис ожидает асинхронный MDN-чек от сервера партнера для подтверждения юридической доставки.

**UC-2: Прием авизо об отгрузке от портового терминала (Inbound Despatch Advice)**
1.  Портовый терминал присылает файл EDIFACT DESADV (Despatch advice) по протоколу AS2 или загружает на SFTP.
2.  Сервис проверяет S/MIME подпись партнера, отправляет ответный MDN-чек и парсит файл.
3.  Извлеченные данные о номерах контейнеров и печатях трансформируются в каноническое событие `ExternalCargoDispatchedEvent` и публикуются в Kafka.

## 4. Функциональные требования (Functional Requirements)

*   **FR-1:** Сервис ДОЛЖЕН поддерживать протоколы передач: AS2 (RFC 4130), SFTP, HTTPS Webhooks.
*   **FR-2:** Сервис ДОЛЖЕН выполнять парсинг и генерацию стандартов UN/EDIFACT (сообщения IFTMIN, IFTSTA, DESADV, CODECO) и ANSI X12.
*   **FR-3:** Сервис ДОЛЖЕН обеспечивать шифрование и подпись сообщений по стандарту S/MIME (3DES / AES, SHA-256) с использованием X.509 сертификатов.
*   **FR-4:** Сервис ДОЛЖЕН автоматически генерировать и обрабатывать квитанции о доставке MDN (Message Disposition Notification).
*   **FR-5:** Сервис ДОЛЖЕН транслировать распарсенные входящие B2B-сообщения во внутренние события Kafka платформы.
*   **FR-6:** Сервис ДОЛЖЕН хранить историю сырых входящих и исходящих EDI-файлов для разбора юридических споров.

## 5. Требования к качеству и SLA (Non-Functional Requirements)

*   **NFR-1 (Availability):** 99.9% uptime.
*   **NFR-2 (Reliability):** 100% гарантия доставки юридически значимых сообщений (использование механизма автоматических повторов Retry Policy с экспоненциальной задержкой).
*   **NFR-3 (Security):** Хранение приватных ключей и сертификатов контрагентов строго в изолированном секретном хранилище (HashiCorp Vault).
